# 交付方式决策

只在需要选择技术载体、数据存储或分发方式时读取。先按使用方式选择架构，不从用户听过的框架名反推需求。

## 单 HTML 原型

适合个人、单机、快速验证、数据规模较小的第一版。可用浏览器本地存储，但必须提供显式导出备份与恢复能力，并说明浏览器清理站点数据、换浏览器、重装或文件来源变化可能带来风险。

优点是交付快、可复制、无需安装；限制是文件访问、后台任务、权限和可靠迁移能力弱。

## 标准 Web 应用

适合跨设备访问、多人协作、账号权限、可靠云端数据和在线更新。通常需要后端、数据库、认证、部署、备份和安全策略。不要承诺仅靠前端实现这些能力。

## 本地桌面应用

适合离线使用、交付安装包、本地文件可备份、系统通知或更稳定的本机数据保存。

- `Tauri`：通常更轻，适合重视安装包体积、性能和本地能力的长期产品；需要匹配具体 Tauri 版本与插件 API。
- `Electron`：生态成熟、Web 技术一致性高，适合需要丰富桌面集成或团队熟悉 Node.js 的项目；安装包和内存通常更大。
- 简易网页封装工具：适合验证，复杂本地能力和维护性有限。

本地数据优先考虑应用数据目录中的 JSON 或 SQLite，并提供用户可见的备份或恢复入口。说明 Windows、macOS 等目标系统与签名、安装、升级需求。不要给未经目标版本核验的配置片段。

## 混合策略

如果用户先验证需求、后面再分发，推荐分阶段：

1. 先用单 HTML 或普通 Web 前端跑通核心闭环。
2. 用真实数据验证字段、状态和流程。
3. 再决定桌面封装、数据库或云端多人协作。

只有当安装、本地文件、离线或系统能力从第一天就是硬要求时，才直接采用桌面架构。

## 决策问题

以下任一答案为“是”时，会改变架构：

- 多人是否同时编辑同一份数据？
- 是否需要跨设备实时同步？
- 是否含敏感数据或角色权限？
- 是否必须离线？
- 是否需要本地文件、系统通知、托盘或自动更新？
- 是否要给非技术用户安装，并长期升级维护？
